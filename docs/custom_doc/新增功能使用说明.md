# 新增功能使用说明

本文整理 `bed97f06f` 及之后在当前分支新增的自定义功能，覆盖权重懒加载、权重分层释放、后台并行加载、CLI 交互命令以及模型加载 IO 速度统计。

## 1. 权重懒加载

新增提交：`f9ed04c9c`

模型加载阶段只同步读取 GGUF 元数据、词表和 tensor 描述信息，并创建占位 buffer；真实 tensor 内存分配和权重数据读取会延迟到第一次 `llama_encode()` 或 `llama_decode()` 前执行。

使用方式：

```bash
./build/bin/llama-cli -m /path/to/model.gguf -p "你好" -n 32
```

该能力默认生效，不需要额外参数。第一次推理前如果权重尚未就绪，内部会调用 `llama_model::ensure_tensors_ready()` 阻塞加载。若加载失败，会记录错误并禁止重复重试，后续推理会直接返回错误。

适用场景：

- 缩短 `llama_model_load_from_file()` 的同步阻塞时间。
- 让模型元数据初始化与后续运行时初始化解耦。
- 为权重按需释放和后台并行加载提供基础。

注意事项：

- 首次推理可能承担完整权重读取和上传成本。
- `vocab_only` 和 `no_alloc` 模式不会触发真实权重加载。

## 2. 权重分层释放与按需重载

新增提交：`862f609e5`

模型支持按 tensor 卸载权重内存，并在后续推理需要时自动重新加载。该功能依赖每个主权重 tensor 独立 backend buffer 的管理方式。

CLI 使用方式：

```bash
./build/bin/llama-cli -m /path/to/model.gguf
```

进入交互后：

```text
/list_weight
/unload blk.0.attn_q.weight
```

`/list_weight` 会列出主权重 tensor 的名称、驻留内存大小、形状和加载状态。`/unload <layer_name>` 会释放指定 tensor 的 backend buffer，并显示释放的 human friendly 字节数，例如 `12.00 MiB`。

`llama-completion` 中同样支持：

```bash
./build/bin/llama-completion -m /path/to/model.gguf -cnv
```

进入交互后使用相同命令：

```text
/list_weight
/unload blk.0.attn_q.weight
```

约束：

- 只能卸载主权重 tensor，view tensor 不能单独卸载。
- 已卸载 tensor 再次卸载会返回 `already unloaded`。
- 后续推理触发按需加载后，该 tensor 会重新变为 `loaded`。

## 3. 后台并行预加载

新增提交：`f61960770`

`--parallel-load` 会在 `llama_context` 初始化完成后启动后台线程预加载延迟权重。这样可以把部分权重 IO/上传与 context、scheduler、KV 等初始化后的准备阶段重叠。

当前实现会在后台加载线程内提前完成 GGUF 元数据解析。显式开启 `--async-io-load` 后，真实 tensor 数据读取阶段会按文件偏移构建多个地址连续的 IO 队列。每个队列由独立 worker 使用随机读接口读取，不共享 `seek()` 文件偏移；CPU/host tensor 会直接读入目标地址，非 host tensor 会先并发读入临时 staging buffer，再串行调用 backend 上传接口。

使用方式：

```bash
./build/bin/llama-cli \
  -m /path/to/model.gguf \
  --parallel-load \
  --async-io-load \
  --load-micro-stats \
  -p "Hello" \
  -n 32
```

也可以显式关闭：

```bash
./build/bin/llama-cli -m /path/to/model.gguf --no-parallel-load -p "Hello"
```

环境变量：

```bash
LLAMA_ARG_PARALLEL_LOAD=1 ./build/bin/llama-cli -m /path/to/model.gguf -p "Hello"
LLAMA_ASYNC_IO_QUEUES=4 ./build/bin/llama-cli -m /path/to/model.gguf --no-mmap --async-io-load -p "Hello"
LLAMA_ARG_LOAD_MICRO_STATS=1 ./build/bin/llama-cli -m /path/to/model.gguf --no-mmap -p "Hello"
```

行为说明：

- `--parallel-load`、`--async-io-load` 和 `--load-micro-stats` 默认关闭，保持兼容。
- 后台线程调用同一套 `ensure_tensors_ready()`。
- 非 mmap 加载在开启 `--async-io-load` 后，会根据硬件并发度启用最多 4 个异步 IO 队列；可通过 `LLAMA_ASYNC_IO_QUEUES` 覆盖。
- 每个队列内的 tensor 按 GGUF 文件地址递增读取，减少随机跳转，同时用多个队列提高手机 UFS/NVMe 等存储的 in-flight 读取深度。
- `--mmap` 路径仍沿用 mmap/page fault 机制，不走显式异步 IO 队列。
- 如果推理先到达权重使用点，会等待后台加载完成或接收加载错误。
- 模型析构时会 join 后台加载线程，避免释放与上传并发。
- `--load-micro-stats` 会额外打印 total ready、buffer alloc、read wall、worker sum、upload wait 和 backend upload set 等加载阶段微观指标。

## 4. 模型加载 IO 速度统计

新增于当前任务。

性能统计中新增模型加载 IO 速度估算：使用模型 tensor 总字节数除以模型加载耗时，输出为 human friendly 单位。

使用方式：

```bash
./build/bin/llama-cli \
  -m /path/to/model.gguf \
  -p "你好" \
  -n 16 \
  --show-timings
```

输出中会出现类似：

```text
load IO speed : 812.34 MiB/s / 1002.00 MiB
```

字段含义：

- `load IO speed`：`模型 tensor 总字节数 / load time` 的估算速度。
- 斜杠后的大小为用于估算的模型 tensor 总字节数。

注意：该统计是端到端加载速度估算，包含 mmap page fault、backend buffer 分配、权重上传等加载路径成本，不等同于纯磁盘吞吐。

### 6.7 实验分支 staging buffer 预申请

测试时间：2026-05-11

分支：

```text
experiment/async-io-prealloc-buffer
```

实验内容：

- 在异步 IO worker 启动前，为每个 IO 队列预申请一个 staging buffer。
- 每个 staging buffer 的大小等于该队列内最大非 host tensor 的大小。
- 非 host tensor 读取复用该队列 staging buffer，避免读取权重时按 tensor 反复分配临时 buffer。
- 多个队列仍可并发读取；backend upload 继续由 upload mutex 串行保护，因此 I/O 读取可以与其他队列的 backend upload 重叠。

手机 Vulkan 验证命令：

```bash

```

关键日志：
